# Planner Domain COMMAND GUIDE

## Naming Conventions & Rules
- **plannerRequest**: The object containing user-input requirements, matching the ubiquitous language (e.g., date, startTime, anchorSchedules).
- **dailyData**: The canonical per-day constraint array derived from `plannerRequest`; each item contains day/date, start/end time, start/end location, and anchors.
- **normalizePlannerRequest**: Converts current flat form data and legacy per-day data into the canonical `dailyData` contract.
- **enforcePlannerConstraints**: Reconciles probabilistic AI output with authoritative user constraints before rendering or saving.
- **generateOptimizedItinerary**: The core function that communicates with the Gemini AI. 

## Architectural Principles
- **AI Prompts**: Prompt/schema construction lives in `functions/itinerary-prompt.js` after the server migration; never ship it or the AI key to the browser. `gemini-optimizer.js` sends constraints and removes model-asserted place identities before constraint enforcement.
- **Hard Constraints**: Departure, destination, day boundary times, and anchors MUST NOT rely solely on prompt compliance. Keep deterministic normalization/enforcement in `planner-constraints.mjs`.
- **Generation contract**: The model emits optional visits only (`attraction`, `dining`, `leisure`), including an empty item array when no visit fits. Keep every requested day/date. The app inserts fixed stops; existing saved payloads are unchanged. Per-day allowed search-center names come from the sanitized user locations, and budget never changes the app's public-transit routing.
- After enforcing generated boundaries, a multi-day day with a gap of at least three hours gets at most one provisional attraction. Places must verify it and measured routing may still remove it. Short days and saved/shared snapshots are unchanged.
- **Form UI**: The `travel-form.js` component ONLY collects data, handles debounce/loading states, and dispatches the customized data via an Event Bus or custom events.
- **Error Handling**: 429 Too Many Requests or other AI API errors are caught and thrown in `gemini-optimizer.js` and properly surfaced to the user in the main app lifecycle.
- **Tests**: Any planner contract change MUST update `test/planner-constraints.test.mjs` and pass `npm test` plus `npm run build`.

## Input Draft

- Ionic `/plan` exit uses the common Yes/No confirmation. No/Escape keeps URL, form and recovery data; Yes clears the entire session/local/in-memory draft and cached form, then navigates. Browser Back restores the indexed `/plan` entry before asking. Native reload/close uses the browser's mandatory generic confirmation and clears on actual `pagehide`, never on a cancelled `beforeunload`. Generated-result navigation skips the prompt after success clears the draft; the result's own 뒤로 on an unsaved generated result (bare `/view`) asks the same Yes/No confirmation first, stays on the result on No or Escape, and on Yes copies the result's `request` back into the draft (the restore '이 조건으로 다시 만들기' uses) before going back, so the review shows the inputs again; saved, shared and guest results go back without asking, except that a result just saved from that generation also gives its `request` back to the planner, because saving replaces `/view` and leaves the planner directly behind it; the question closes when the route changes; browser or hardware Back is unchanged; confirmed exit invalidates the local generation attempt so late responses cannot restore inputs or redirect. While a generation runs, every guarded exit (page 뒤로, `window.navigate`, browser or hardware Back) asks to stop instead (`plan-exit-requested`): 계속 기다리기 keeps waiting, 멈추기 makes the attempt stale and returns to the review with the inputs kept, and a result that arrives first still opens `/view` and closes the question. The server request is not cancelled, so a stopped generation that succeeds still uses its credit; the question says so (unlimited accounts get the same question without the credit sentence). This policy supersedes draft restoration across a confirmed plan exit; it does not delete saved itineraries.
- The explicit destination-edit button is an exception: `/destination` navigation carries `state.returnTo: '/plan'`, skips confirmation and preserves the draft. In this edit flow, changing cities retains dates, preferences, endpoints, stays, daily overrides and anchors (the one exception to one-city drafts: the user is moving this trip, so its inputs move with it and are edited in the form); continuing returns to `/plan`. Ordinary destination creation retains its existing city-change reset and preference flow. The destination action sits beside its label, and both endpoint labels use equal-height heading rows.
- Explicit theme/budget edits from the form or review also carry `state.returnTo: '/plan'` to `/preference/2` and skip exit confirmation. Save current form input before opening the preference editor. Selection changes and skip update only preferences; dates, destination, endpoints, stays, daily overrides and anchors remain in the shared draft. Normal Back/Home exits still require confirmation.
- The date-edit action sits before theme/budget and opens `/preference/1` with the same explicit return state, preserving the draft without a leave prompt. In this mode, `setStep(1, { returnToPlan: true })` labels the action as applying dates and returns directly to `/plan` with return state. Reuse `moveTripDates` for date/duration updates. Ordinary date creation still goes to `/preference/2`; cached re-entry must reset the edit mode. Date-editor Back/other navigation and native reload/close use the same confirmation/discard policy as `/plan`, while explicit Apply returns without confirmation.
- In the handoff form, destination uses the translated `country / city` from the shared catalogue, including language changes and review. Start/end dates share one row even on mobile and are readonly text; date changes go through the explicit date editor, while submission retains the draft's date array. Keep one shared daily-time toggle below both time inputs. Stay removal is a translated text action in the card heading and preserves other inputs.

- `services/planner-draft.mjs` owns the editable flat input shared by preference selection, form restoration, and editing a saved itinerary. `currentFormData` is its per-tab recovery copy; `userPreference` is only a compatibility projection for route guards.
- Editing a saved itinerary replaces the whole input draft before navigation. Displayed dates, preference badges, anchor day options, daily-time inputs, and submitted data must use that same draft. `travel-form-data.js` receives it explicitly and must not reread session storage.
- Preference controls update the draft only on explicit user changes, not while reconstructing controls. Re-entering the preference page restores the current draft; skipping clears theme and budget, including explicit null values.
- Keep only editable fields in the draft. Saved derived `dailyData` must be rebuilt by `normalizePlannerRequest` after editing, so it cannot resurrect old dates, times, or deleted anchors.
- Form reset clears detailed inputs while preserving the selected dates/theme/budget. The cleared draft must also survive reload.
- Multi-day drafts use the first departure, final destination and explicit `overnightLocations`. Never infer lodging from legacy daily endpoints; restore the last day's destination and ask for missing stays when editing. `sameOvernightLocation` repeats the first selected stay for every night. Duration changes resize this array, and a day trip clears it. Saved/shared snapshots are unchanged until explicit regeneration.

- The form's `where-to-go` native dialog reuses `home-recommendations` with `planner-pick`. Offer the existing six-city catalogue, select a visit day, and add untimed mandatory visits without replacing endpoints, lodging or bookings. Cancel changes no fields; repeat selections must not duplicate visits. Destination catalogue picks do not claim measured proximity. The route mode uses `route-discovery.js` to sample up to three points on at most two measured fixed-stop legs, then verifies inbound/outbound travel and a 60-minute stay before offering a detour of at most 20 minutes. Untimed required visits are provisionally placed first without editing the draft. Unknown hours stay explicit, known closures are excluded, and other-day identities are reserved. Each pick is checked individually and generation rechecks the whole trip. Cancel, day/mode changes and changed drafts invalidate pending results; adding a pick preserves its selected Place ID.

- Each night offers `find-stay`: a native dialog builds a Booking.com search link from an explicit area, guest count and that night's dates (all nights in consecutive-stay mode). It does not fetch live prices or book rooms. Selecting a property uses the existing place snapshot and applies only to the selected night, or all consecutive nights; cancel/search never replace lodging.

## Wording and Step Count

- One user-facing term names the anchor list everywhere a user picks or edits it: '꼭 갈 장소' / 'must-visit place' (form section, add buttons, errors, discovery and course copy). '고정 일정' / 'fixed visit' stays only where it means a visit with a fixed time (overlap and travel-time warnings, anchor conflicts, public-course notices). Day numbers come from `t('day_n')` ('1일차' / 'Day 1') in the form, review and validation prefixes; elements built in code carry `data-day-n` so `updateTexts` rewrites them on a language switch.
- The planner is seven steps (country, city and places on `/destination`, then dates, style, details, review). `ui/step-progress.js` draws the counter and the bar from the same count: 4/7 and 5/7 on `/preference/1` and `/2`, 6/7 on the handoff form and 7/7 on its review.

## Input Validation Boundary

- `functions/planner-request-validation.mjs` is the dependency-free canonical `dailyData` validator shared by the form, optimizer and server. It lives under `functions/` so Firebase packaging includes it; the browser imports only this pure module, never server SDKs or prompts. The server's configured Node 24 runtime can require this synchronous ES module from CommonJS.
- `generateItinerary` checks authentication, then validates the raw canonical request **before** sanitization, account reads, secret access or Gemini calls. Invalid input returns `invalid-argument` with safe reason/field indexes, not input text. The sanitizer only projects/clamps validated fields; it must not be used to prove validity or invent a day for empty input.
- Require 1–4 ordered calendar dates, matching date/day representations, valid same-day `HH:mm` ranges and non-empty departure/arrival locations. Anchors are optional, but submitted anchors need a name and valid times within their own day's range, including custom daily times; do not silently truncate more than 10 anchors per day.
- Untimed required visits stay in the editable draft with `flexible: true`. Before canonical validation and submission, the form assigns times around fixed reservations using measured Maps legs and known opening hours. Reject visits that cannot fit or are known closed; if no candidate can be measured, explain the route lookup failure instead of inventing a travel time. Preserve `flexible: true` on the client result so measured route fitting can update its provisional time without moving fixed reservations. The server continues to receive only timed anchors.
- Keep the existing optional-anchor-location policy and ignore untouched empty UI rows. Preserve explicit empty custom times through normalization so global defaults cannot mask them. The form owns row-specific feedback/focus and the existing local-calendar past-date check; no server timezone/past-date policy is introduced here.
- `planner-validation.js` translates safe reason codes. `functions/invalid-argument` must surface as a correctable error. Auth failures, credits-empty and generation-in-progress keep their own messages; every other failure throws `generationAiFailed` with `retryable` true only when the server failed the call (a plan it returned already used its credit). A client timeout or a lost connection (the SDK's bare `internal`) throws `generationOutcomeUnknown` without a retry, because the server may still finish, spend the credit and hold the lease. That error carries `outcomeUnknown`, and an unlimited account sees `generationOutcomeUnknownUnlimited` (no credit sentence). No mock itinerary is ever built.
- Validation changes must pass the planner request, server callback, optimizer error, and planner constraints tests, plus the browser validation/draft/generation scenarios.

## Generation Lifecycle

- The active `/plan` is `PlanScreen` in `src/prototype/ionic-screens.jsx`. It lazy-loads `travel-form.js` and `services/gemini-optimizer.js`, then handles the form's `generate-itinerary` event by calling `generateOptimizedItinerary`.
- Each attempt takes a new `run` number. Leaving `/plan`, a query change on `/plan` (such as `?review=1`), discarding the draft (`planner-draft-discarded`) or a different signed-in user makes the attempt stale, and a stale attempt never applies its result. This does not cancel the server request.
- Phases are form, loading and error. Loading lists three stages (일정 초안 만들기, 장소 확인, 이동시간 계산): `generateOptimizedItinerary(request, { onStage })` passes `onStage` to `verifyGeneratedItinerary`, which reports `places` and `routes`. The list is visual; a visually hidden line in the status region carries the current stage for screen readers. A static line says it can take over a minute. Error shows the message, '다시 시도' (same request, only for a retryable error) and return-to-form; the draft is kept. While the review's map checks run before generation, 일정 생성하기 reads '입력 확인 중…'. On success it keeps the plan in memory for the same user (used once by `/view`, not persisted), clears the draft and navigates to `/view` at once; there is no result button. Only the current attempt releases the form via `itinerary-generation-complete`.
- Ionic coverage is `test/browser/ionic-shell.spec.mjs` (success to `/view`) and `test/browser/ui-handoff.spec.mjs` (stages, stop on every Back, a late result after stopping or leaving, a result during the stop question, retry, re-read credits).
- Keep generation request/response constraints in the existing planner services (`gemini-optimizer.js`, `gemini-fallback.mjs`), shared by both shells.

### Legacy vanilla shell

`src/app/generation-controller.mjs` and `ui/generation-progress.js` are imported only by `src/app/main.js` (loaded by `index.html`). The legacy shell is still served by `npm run dev:legacy`, built by `npm run build:legacy`, and exercised by the `npm run test:browser` smoke suite that `npm run check` runs, so keep these rules:
- `src/app/generation-controller.mjs` owns the active generation attempt, success/failure transitions, and result/navigation guards. `src/app/main.js` wires the form event, auth/route context, result application, and completion notification into it.
- Call `syncContext()` on route/auth reevaluation. Leaving `/plan` or changing accounts invalidates the local attempt immediately; returning to `/plan` does not revive it. This does not cancel the server request.
- Only the current attempt may apply its result, change the progress screen, or release the form's submit button via `itinerary-generation-complete`. A superseded request's completion must not stop a newer request's timers.
- `enterPlan()` restores the form when idle but preserves the current loading/success/failure screen on same-account, same-route reevaluation. Successful generation waits for the user to choose the result button before navigating.
- `ui/generation-progress.js` owns loading/result/error markup updates and advertisement/message animation resources. Every stop clears intervals, delayed transitions, and animation frames; version checks also ignore callbacks already queued before cancellation.
- Lifecycle and presentation changes are covered by `generation-controller.test.mjs` and `generation-progress.test.mjs`.

- Optional `dailyLocations` holds explicit per-day departure/arrival overrides. Blank fields inherit trip endpoints or nightly stays; never infer overrides from legacy `dailyData`. Normalize before flexible-visit placement, validation, generation and boundary enforcement. Turning off clears overrides; a day trip clears them, and duration changes trim removed days. The form shows default places and warns when consecutive day boundaries need a separate transfer (not included in daily route calculations).

- Successful generation calls `generated-day-quality.js` before showing the result. Resolve physical identities, await live opening hours and reuse the timeline's measured fitter for every day, including unopened tabs. Sparse recovery uses `fillMeasuredGaps` only after actual routes; never insert provisional visits from raw clock gaps. Provider failures preserve the generated itinerary with unknown evidence rather than inventing routes or converting it into a mock. Flexible required visits are chosen by earliest feasible opening slot; remeasure outbound travel after waiting.

## Ionic UI handoff (2026-10-08)

- Screen motion follows root `AGENTS.md`: the Ionic shell handles every route/tab lifecycle, and destination/recommendation/course steps use `useStageTransition` without replacing the page. Form review and native stay/discovery dialogs reuse `src/ui/screen-motion.js`; generation phases retain the same form element. Reduced motion suppresses these transitions without delaying navigation or data writes.

- `/destination`, `/recommend` and `/courses` share the destination catalogue: 24 cities across Korea, Japan, France, Taiwan, Thailand, Vietnam, Singapore, Italy, Spain, the UK and the US. Country options come from the server's `TRAVEL_REGIONS`. The canonical server checks the city/country pair, selected ID/address/coordinates, local time zone and fixed appointment overlaps. Legacy requests without destination metadata remain supported. `functions/travel-region.mjs` owns region/time-zone conversion including DST; US support covers New York, Los Angeles, San Francisco, Las Vegas, Chicago, Washington DC and Honolulu, each with six translated places. The region helper selects Pacific/Central/Eastern/Hawaii time by city; Honolulu does not use DST, and requests without a city retain the existing New York fallback.
- The handoff form stores optional `stays` with check-in/check-out ranges, derives nightly endpoints, and uses the chosen city for undecided nights. Reject overlapping/reversed/out-of-trip stays; shifting the start date shifts ranges and preserves explicit daily overrides. The legacy per-night UI remains a compatibility path.
- Undecided nights keep `destination.name` as the machine endpoint; `makeBoundaryItem` adds a localized `stayUnsetLabel` ('숙소 미정 (서울 중심)') used for the title instead of the English name, with no Maps search link. The form's daily default line uses the same label.
- Place picks carry no `day`; a copied course's stops share one `day` (each new course takes the day after the latest one), so a course stays together. `spreadVisitDays` runs in `populateForm` and gives each flexible pick without a day inside the trip the day with the fewest anchors; once the form saves, the shown day is explicit. Only the first flexible row shows the opening-hours hint.
- The generation credit balance is the first line of the plan form and sits above 일정 생성하기 in the review. A known zero disables 일정 생성하기 with a note that no more credits are available and inputs are kept, and the button's `aria-describedby` points at that note; an unknown balance (loading, offline, failure) leaves the decision to the server. Each generation attempt re-reads the balance. A different signed-in account resets the balance to loading before its own read, and a read that finishes after the page left or the account changed is dropped. The credits-empty error does not promise rewarded ads, which are paused.
- The owner-scoped local recovery copy `compasser.planner.v1` complements the existing session draft. Remember country/city stage and `/plan?review=1`; account changes clear personal drafts, guest sign-in can claim its draft, and generation success clears recovery. Report failed writes without undoing in-memory input.
- The first submit waits for pending place picks and opens the review. The review lists every blocker the inputs alone show, at once and each with its own 수정: required fields, a past date, start not before end (per day when custom), an incomplete shown flight, missing or unselected places, invalid stays and incomplete visits (a visit needs a searched place; a visit without times also offers 자동 배치로 변경). 일정 생성하기 stays disabled while any remain, and while the pre-generation checks run, as for a known zero balance; empty times read '시간 미입력'. The final submit checks snapshot identity, stays, fixed time overlap, actual travel and known hours, then uses existing flexible placement and canonical generation/credit handling. Never generate while restoring, changing preference, or reviewing.

## Course discovery navigation

- Ionic `/courses` opens country selection, then city selection, then the course browser. `/recommend` and `/courses` keep the step in the URL (`?country=<code>&city=<id>`, validated against the catalogue) and push one history entry per pick, so Back and reload keep the user's step. Reuse all six curated Korean cities and the existing Japanese/French destinations. Do not mount/fetch course lists before city selection or mutate the planner draft while browsing.
- Pass the chosen `city` to `home-courses` and `public-courses`; show only that city's curated/public records. Scoped public lists retain search, duration, pagination and reviews, without a second city selector. A polite status line reports the filtered count or the empty result; '조건 초기화' appears only when a user filter empties the list, and the hint mentions loading more only while another page exists. Missing courses stay an honest empty state.
- Back returns to city selection, then country selection, then home. Preserve the selected browser state across the existing login/review return route. Legacy unscoped widgets retain their existing full catalogue and city filter.
- A `/courses?review=<public course id>` link (English route page, `/home?review=` redirect, post-login return after a reload) reads only that course with `getPublicCourse`, opens the first catalogue city whose aliases list it (`courseCity`, the same match as `filterCourses`) by replacing the address with that country and city (keeping `review`), and `public-courses` opens its review panel. Unknown, curated or unreadable ids stay on country selection; curated courses have no reviews. A course that is gone, or a lookup that fails, says so above the picker (`courseReviewMissing` / `courseReviewUnavailable`) until the user picks or goes back; a public course outside the catalogue cities stays silent.

- Offline, a traveler-course load that fails shows the last list loaded in this tab (the list is global, each city filters it) with an offline note instead of an error, hides retry and load-more, and reloads by itself on `online`, retrying the same kind of load and reopening the review panel that was open. The review panel loads public reviews as soon as it opens instead of waiting for Firebase Auth to report its state (slow on a weak or lost connection), and loads again only when the account changes; it says loading failed (`courseReviewsLoadError`) or that the user is offline (`courseOffline`), never 'couldn't process'. Failures while online keep the retry button and never reload by themselves.
- Home no longer links directly to the English route directory. After country/city selection in `/courses`, each curated/public card uses `courseEnglishLink` (이 코스 영어로 보기 / Open shareable page) to open its existing English route page. Profile sharing/QR labels and public directory URLs remain unchanged.

## Recommendation discovery navigation

- Search input never removes the regular place catalogue; its named `details` section can be collapsed explicitly. `AIPlaceRecommendations` is shared by `/recommend` and `/destination` without changing page identity. Visit dates are local recommendation context, not draft edits; only explicit verified-place add/remove changes anchors. Date/language/preference/city/route changes invalidate late responses.
- `recommendPlaces` is a bounded callable separate from itinerary generation. It validates server-owned city scope, uses Weather and search-grounded Gemini evidence, then verifies canonical Google Places identities, geography and operational status. Display actual citations, Google Maps attributions and isolated required Search suggestions. Never claim forecast/popularity without evidence or cache provider responses. Persistent guest/global limits bound costs; see `docs/history/AI_PLACE_RECOMMENDATIONS_2026-10-14.md` for required server secret/APIs and deploy steps.
- Recommendation reasons use a provider-supported text segment and only that segment's grounding chunk URLs. Validate the original segment; strip markdown bullets/emphasis only for display. Preserve original chunk indexes when rejecting unsafe sources; the formatter may select an evidence index and extract event dates, but cannot write a reason or choose arbitrary citations. Require the venue name in the selected segment. Time-limited event/exhibition claims need an event name and valid full-year ISO start/end dates in that same segment, with the visit date inside the inclusive range; reject missing, inferred or conflicting dates before Places requests. Generic permanent museum descriptions do not require event dates. A separate timeless supported candidate may still pass. This is provider grounding, not independent source-page fact verification, and conservative filtering may reduce the result count.
- Verify the evidence venue name at Unicode word/Korean-particle boundaries, not as a substring of another name (e.g. a museum versus its station). Keep reasons about venue characteristics; reject common dynamic hours/forecast/live-ranking assertions before Places lookup and display structured verified weather/hours separately. The lexical guard is deliberately conservative and is not a semantic fact checker. `validRecommendationWeather` is shared by server and client: reject empty/invalid forecast payloads, reversed temperatures and out-of-range precipitation; zero degrees/zero probability remain valid. Malformed current hours must remain unknown instead of falling back to weekly hours. See `docs/history/AI_RECOMMENDATION_REVIEW_2026-10-16.md` for repros and remaining limits.
- Undated event statements are never shown. If every statement about a Places-verified venue cites an undated event, show the venue with Places facts only (`type · district`, `reasonKind: 'place-info'`, Google Maps as the single source) after grounded venues; other gate failures still drop the venue. Decided 2026-10-19. A formatter event whose name does not appear in a statement that also has no event wording or dates is ignored, so the timeless statement is shown; a missing event field is still treated as an event (decided 2026-10-21).
- Retry the grounded search call once only when its response has neither search queries nor grounding chunks (the model answered without searching; Gemini 2.5 bills only prompts that searched). Any other grounding failure is not retried. A second miss still fails as `recommendation-sources`; the retry logs `[recommendPlaces] search-retry`. Added 2026-10-19; since 2026-10-21 the retry goes to the backup model.
- The grounded search call uses `gemini-2.5-flash` with thinking off (`thinkingBudget: 0`); the formatting call stays on `gemini-2.5-flash-lite`. flash-lite skipped Google Search twice in a row in production (no queries, chunks or search entry). Decided 2026-10-20.
- Backup model `gemini-3.5-flash-lite` (decided 2026-10-21): any error from a 2.5 call (HTTP error, timeout, empty or truncated answer) repeats that one call on the backup and logs `[recommendPlaces] backup-model`; a backup error fails the request. The no-search retry also uses the backup, which searched in 10 of 10 local runs. Gemini 3 rejects `thinkingBudget` (HTTP 400), so backup calls send `thinkingLevel: 'minimal'` instead. A request makes at most five AI calls: the search and its fallback, one no-search retry, the formatting and its fallback.
- Parentheses may identify a branch or facility. Unwrap a parenthesized translation only when both names belong to the same reviewed city/venue group; otherwise verify the full name. Apply this rule to evidence matching, Places identity and refresh exclusion together.
- AI discovery prefers venues outside the default catalogue, then balances culture, nature, food, shopping and unknown groups within the same overlap priority. Use canonical Google Places `primaryType`, falling back to `types`; never trust a model-supplied category. Inspect at most six grounded candidates before choosing at most four, retain Place ID/name deduplication and all evidence/identity gates, and keep four verified results if a later optional lookup fails. Unknown types stay in one `other` group. Catalogue venues may fill remaining slots; do not force missing categories or add unverified places. `functions/recommendation-defaults.mjs` packages the default UI names/local names/reviewed aliases for the server, and a catalogue sync test must stay green when either catalogue or translations change.
- AI discovery offers one optional recommendation-only `interest`: `any`, `indoor`, `walk`, `culture`, `food`, `discovery`, shared by UI and server through `functions/recommendation-interests.mjs`. Defaults to `any` when absent; reject other values before account/provider work and echo it in responses for client scope validation. An explicit interest guides this search ahead of the saved trip theme, while keeping budget/date context and all place/evidence gates. Selecting it never edits the draft or auto-fetches; use the existing explicit recommendation button. Layout-time invalidation clears results/errors/busy state on context changes and ignores previous successes, errors and finalizers. Preserve page/form identity, shared semantic stage transitions and keyboard focus. Interest survives a cached widget instance but resets on a new city/widget or reload. Deploy the updated callable before the new client because the old callable rejects the new input field.
- AI place identity accepts exact normalized names or reviewed names in the same city/venue group from `RECOMMENDATION_NAME_GROUPS`. Since 2026-10-19 it also accepts a name that adds or drops whole leading words (대한불교조계종 봉은사 = 봉은사, 대학로 마로니에 공원 = 마로니에공원) when the shorter name has at least three letters; a different last word (봉은사역, … 본관) is still a different place. Since 2026-10-21 a multi-word name's last word may also differ only by a final 관 (국립현대미술관 서울관 = 국립현대미술관 서울, not … 덕수궁); a one-word name never loses it. A leading legal-entity mark ((재), (주), (사), (유), ㈜) is dropped and a middle dot counts as a space before these checks ((재)환기재단·환기미술관 = 환기미술관; (주)아트레온 ≠ 아트레온 갤러리). Never flatten those groups for identity matching or accept model-invented aliases. Reject ambiguous different Place IDs, except duplicate listings of one venue (decided 2026-10-20): ignore transit/parking listings, then merge the rest when at least one has a Google type, none is food, shopping or a store, and all lie within 1,000 m (every listing a park/nature/mountain/island type) or 300 m otherwise; choose the first typed listing and log `[recommendPlaces] merged-duplicates`. Reject wrong countries/cities, invalid/out-of-bound coordinates, closed and future-opening businesses. Prefer locality/postal town; only listed metro/prefecture cities may match admin level 1, and other admin level 2 matches require no locality. New York state and Los Angeles County alone are not city matches; boroughs and the existing Santa Monica catalogue destination are explicit allowances.
- AI discovery requests `currentOpeningHours` and `regularOpeningHours` in the existing Text Search call (still at most six, now Enterprise field tier). `recommendationHours` evaluates any open interval on the venue-local visit date, not `openNow` or an actual scheduled time. Current dated periods apply only today through day six, including special-day overrides; use weekly hours otherwise, but never fall back through malformed current periods or an unresolved special day. Handle overnight/week rollover, 24/7 and truncated boundaries. Reject known full-day closure; keep absent/invalid hours as unknown.
